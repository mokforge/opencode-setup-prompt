# Python: Frameworks and libraries: web, databases, settings, logging, CLI

## Choosing tools

The framework, ORM, and the configuration and logging approach are already chosen by the project. Use them and their conventions. For a new service, do not choose on your own: propose options with reasons (see "Choice" below) and get user approval.

## Choice (new services only)

| Task                                                   | Suitable option                                              |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| Typed API with async and automatic docs                | FastAPI                                                      |
| Site with an admin panel, ORM, and auth out of the box | Django                                                       |
| Small service, maximum simplicity                      | Flask                                                        |
| CLI utility                                            | Typer (or standard `argparse` with no dependencies)          |
| Background jobs                                        | the queue adopted by the project (Celery, RQ, arq, Dramatiq) |

## Web layer (general rules)

- Keep request handlers thin: parse and validate input, call a service, build the response. Business logic lives in the service layer; database access lives in repositories.
- Describe input and output with models (pydantic in FastAPI, forms/serializers in Django). Do not accept or return raw dictionaries.
- Translate domain errors into HTTP responses in one place (an exception handler), with a consistent error body format.
- Perform authorization and permission checks before business logic, on every protected route.
- Treat input as untrusted: validate sizes, types, and ranges.
- Version the public API; make breaking changes only with a new version.
- Pass dependencies (database session, current user, settings) through the framework's mechanism (`Depends` in FastAPI), not global variables.

### FastAPI

- Group routes in `APIRouter` by area; use `Depends` for dependencies; manage resource lifecycle with `lifespan`.
- `response_model` defines the output schema so extra fields are not returned.
- Synchronous blocking calls inside an `async def` handler are forbidden (see `async.md`); for synchronous code, declare the handler as `def`.

### Django

- Keep business logic out of views and signals; keep migrations under version control, each in its own commit with the model change.
- Queries: use `select_related` and `prefetch_related` to avoid N+1; use `only`/`values` for heavy result sets.

### Flask

- Use an application factory (`create_app`), blueprints by area, and initialize extensions in the factory.

## Databases: SQLAlchemy and Alembic

- A session lives for a request or a unit of work; commit the transaction at the operation boundary, not in every repository method.
- SQLAlchemy 2.x: use typed models (`Mapped[...]`, `mapped_column`) and queries via `select(...)`.
- For async: use `AsyncSession` and an async driver; do not mix synchronous calls into the same session.
- Avoid N+1: load relationships explicitly (`selectinload`, `joinedload`).
- Every schema change has an Alembic migration with `downgrade` if the project writes them. Test the migration on a clean database: apply from scratch, roll back, apply again. Re-read autogenerated migrations: they miss renames and some type changes.
- Migrations contain no business logic and do not import application models (models change, while a migration must stay reproducible).
- Perform dangerous operations on large tables (adding a NOT NULL column or an index) in several steps; agree on the order and locking with the project.

## Settings: pydantic-settings

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="APP_")
    database_url: str
    debug: bool = False
```

- Settings are read once at startup, typed, and validated immediately: with an invalid configuration the application fails at startup, not on the first request.
- Do not commit `.env`; keep an example `.env.example` without values in the repository.

## Logging

- Do not mix `logging` and `structlog` in one project.
- Use structured fields (request ID, user, operation) instead of string concatenation. The request ID is propagated end to end.
- Levels: `debug` for debugging, `info` for significant events, `warning` for a recoverable problem, `error` for a failed operation. Log exceptions with a traceback (`logger.exception`) once, at the handling boundary.

## CLI (Typer)

- A command is a thin wrapper around a library function; test the logic without the CLI.
- Exit codes: 0 for success, non-zero for an error; show user-facing errors without a traceback, with a traceback behind the `--verbose` flag.
- Human-readable output goes to stdout, diagnostics to stderr; provide an optional machine-readable format (`--json`).
- Group subcommands; give each one help text and an example.
