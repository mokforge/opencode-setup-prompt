# Python: Фреймворки и библиотеки: веб, БД, настройки, логирование, CLI

## Правило выбора

Фреймворк, ORM, схема конфигурации и логирования уже выбраны проектом. Используй их и их соглашения. Для нового сервиса выбор не делай сам: предложи варианты с причинами (раздел «Выбор» ниже) и согласуй с пользователем.

## Выбор (только для нового сервиса)

| Задача | Подходит |
|---|---|
| API на типах, async, автодокументация | FastAPI |
| Сайт с админкой, ORM, авторизацией «из коробки» | Django |
| Небольшой сервис, максимальная простота | Flask |
| CLI-утилита | Typer (или стандартный `argparse` без зависимостей) |
| Фоновые задачи | очередь, принятая в проекте (Celery, RQ, arq, Dramatiq) |

## Веб-слой (общие правила)

- Обработчик запроса тонкий: разбор и проверка входа, вызов сервиса, формирование ответа. Бизнес-логика живёт в сервисном слое, доступ к БД в слое репозиториев.
- Входные и выходные данные описаны моделями (pydantic в FastAPI, формы/сериализаторы в Django). Не принимай и не возвращай «сырые» словари.
- Ошибки домена переводятся в HTTP-ответы в одном месте (обработчик исключений), с единым форматом тела ошибки.
- Авторизация и проверка прав выполняются до бизнес-логики, на каждом защищённом маршруте.
- Входные данные недоверенные: проверяй размеры, типы, диапазоны.
- Версионируй публичный API; ломающие изменения только с новой версией.
- Зависимости (сессия БД, текущий пользователь, настройки) передаются через механизм фреймворка (`Depends` в FastAPI), не через глобальные переменные.

### FastAPI

- Маршруты в `APIRouter` по областям; зависимости через `Depends`; жизненный цикл ресурсов через `lifespan`.
- `response_model` задаёт выходную схему, чтобы не отдать лишние поля.
- Синхронные блокирующие вызовы внутри `async def` обработчика запрещены (см. `async.md`); для синхронного кода объявляй обработчик как `def`.

### Django

- Бизнес-логика не в представлениях и не в сигналах; миграции под контролем версий, каждая в своём коммите с моделью.
- Запросы: `select_related` и `prefetch_related` против N+1; `only`/`values` для тяжёлых выборок.

### Flask

- Фабрика приложения (`create_app`), blueprint по областям, расширения инициализируются в фабрике.

## База данных: SQLAlchemy и Alembic

- Сессия живёт в рамках запроса или единицы работы; транзакция фиксируется на границе операции, а не в каждом методе репозитория.
- SQLAlchemy 2.x: типизированные модели (`Mapped[...]`, `mapped_column`), запросы через `select(...)`.
- Для async: `AsyncSession` и асинхронный драйвер; не смешивай синхронные вызовы в той же сессии.
- Против N+1: явная загрузка связей (`selectinload`, `joinedload`).
- Каждое изменение схемы делает миграция Alembic с откатом (`downgrade`), если проект их пишет. Миграцию проверь на чистой БД: применение с нуля, откат, повторное применение. Автогенерацию перечитай глазами: она не видит переименований и часть изменений типов.
- Миграции не содержат бизнес-логики и не импортируют модели приложения (модели меняются, миграция должна остаться воспроизводимой).
- Опасные операции на больших таблицах (добавление NOT NULL колонки, индекс) делай в несколько шагов; порядок и блокировки согласуй с проектом.

## Настройки: pydantic-settings

```python
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="APP_")
    database_url: str
    debug: bool = False
```

- Настройки читаются один раз на старте, типизированы и проверены сразу: при неверной конфигурации приложение падает на старте, а не на первом запросе.
- `.env` не коммитится, в репозитории лежит пример `.env.example` без значений.

## Логирование

- Не смешивай `logging` и `structlog` в одном проекте.
- Структурированные поля (идентификатор запроса, пользователь, операция) вместо склейки строк. Идентификатор запроса сквозной.
- Уровни: `debug` — отладка, `info` — значимые события, `warning` — восстановимая проблема, `error` — отказ операции. Исключения логируй с трассировкой (`logger.exception`) один раз, на границе обработки.

## CLI (Typer)

- Команда: тонкая обёртка над функцией библиотеки; логика тестируется без CLI.
- Коды выхода: 0 успех, ненулевой ошибка; ошибки пользователю без трассировки, с трассировкой по флагу `--verbose`.
- Вывод для людей в stdout, диагностика в stderr; опциональный машиночитаемый формат (`--json`).
- Подкоманды группируются; у каждой справка и пример.
