# Python: Инструменты проекта: менеджер пакетов, pyproject.toml, ruff, типы, хуки, CI, сборка

## Правило выбора

1. Если проект уже использует инструмент (`uv.lock`, `poetry.lock`, `Pipfile`, `requirements*.txt`, `tox.ini`, `.pre-commit-config.yaml`, раздел в CI), работай им. Не мигрируй проект на другие инструменты и не меняй конфиги без явной просьбы.
2. Миграцию предлагай отдельной задачей и согласуй с пользователем; смешивать её с функциональными изменениями нельзя.
3. Значения по умолчанию ниже относятся только к новому проекту или к просьбе «настроить с нуля». Что неясно (минимальная версия Python, система сборки, публикуется ли пакет), уточни, не угадывай.

## Значения по умолчанию для нового проекта

| Задача | Инструмент |
|---|---|
| Окружение, зависимости, запуск | `uv` |
| Линтер и форматтер | `ruff` |
| Проверка типов | `mypy` (строгий режим). `ty` и `pyrefly` допустимы по решению проекта, но на момент написания находятся в бете |
| Тесты | `pytest` (+ `pytest-cov`) |
| Хуки коммита | `pre-commit` (`prek` совместим по конфигу, если проект его уже использует) |
| Система сборки | `hatchling` для пакетов; `uv_build` допустим для чистых Python-пакетов на `uv` |

Минимальную версию Python бери из проекта (`requires-python`, CI, `.python-version`).

## Команды `uv`

```bash
uv init --package имя     # новый пакет с src-layout
uv add пакет              # зависимость времени выполнения
uv add --dev пакет        # зависимость разработки (группа dev)
uv add --group docs пакет # зависимость из другой группы
uv remove пакет
uv sync                   # окружение по lock-файлу
uv lock --upgrade-package пакет
uv run pytest             # запуск без ручной активации окружения
uv run --with пакет python-skills скрипт.py   # разовая зависимость
uv build                  # сборка sdist и wheel
```

- Lock-файл (`uv.lock`) коммитится. В CI ставь зависимости по нему (`uv sync --locked`).
- Не используй `uv pip install` в проекте с lock-файлом: окружение расходится с lock.
- Зависимости разработки лежат в `[dependency-groups]` (PEP 735), а не в `[project.optional-dependencies]`: extras публикуются вместе с пакетом, группы нет.
- Одноразовые скрипты описывают зависимости блоком PEP 723 (`# /// script`) в начале файла.

## `pyproject.toml`: основа

```toml
[project]
name = "имя"
version = "0.1.0"
requires-python = ">=3.11"          # значение из проекта
dependencies = []

[dependency-groups]
dev = ["pytest", "pytest-cov", "ruff", "mypy"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 99                    # PEP 8: 79 по умолчанию, команда может до 99; значение проекта важнее
target-version = "py311"

[tool.ruff.lint]
select = ["E", "W", "F", "I", "N", "UP", "B", "SIM", "S", "C4", "RUF"]

[tool.ruff.lint.pycodestyle]
max-doc-length = 72                 # комментарии и docstring по PEP 8 (правило W505)

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101"]               # assert в тестах допустим

[tool.mypy]
strict = true

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = ["--strict-markers", "--strict-config"]
```

- Набор правил `ruff` расширяй постепенно. `select = ["ALL"]` в существующем проекте приводит к лавине замечаний: включай правило, когда готов исправить найденное.
- Подавление замечания: точечно (`# noqa: КОД` с причиной), не файлом целиком.

## Хуки и CI

- Хуки: `ruff` (проверка с исправлением и форматирование), проверка типов, проверка слияния и больших файлов. Версии хуков закрепляй (`rev`) и обновляй осознанно.
- CI запускает те же проверки, что и разработчик локально, теми же командами. Если CI и локальные команды расходятся, исправь расхождение.
- Матрица версий Python в CI соответствует `requires-python`.

## Миграция (только по просьбе)

- `requirements.txt` + `pip`: `uv init`, перенос зависимостей командой `uv add -r requirements.txt`, удаление старых файлов после проверки.
- `flake8`/`black`/`isort`: заменяются `ruff`; перенеси настройки (длина строки, исключения), старые конфиги удали.
- `setup.py`/`setup.cfg`: перенос метаданных в `[project]`, затем удаление старых файлов.
- `poetry`: сначала проверь, нужна ли миграция вообще; poetry полностью рабочий инструмент.

## Сборка и публикация

- Версия задаётся в одном месте. Релиз: тег в git, сборка `uv build`, проверка содержимого wheel, публикация через доверенную публикацию (trusted publishing) в CI, а не токеном на машине разработчика.
- Не публикуй и не создавай теги без просьбы пользователя.
