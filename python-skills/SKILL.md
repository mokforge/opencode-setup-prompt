# Python

Основные соглашения ниже. Подробные справочники лежат рядом в этом каталоге; читай только нужный (инструментом чтения файла), не все сразу:

- `tooling.md`: менеджер пакетов, `pyproject.toml`, ruff, проверка типов, хуки, CI, сборка, миграция с legacy. Читай при изменении окружения, зависимостей, конфигов, сборки.
- `testing.md`: pytest, фикстуры, моки, async-тесты, БД, покрытие, отладка падающих тестов. Читай при написании и ревью тестов.
- `async.md`: asyncio, `TaskGroup`, таймауты, отмена, типичные ошибки. Читай при работе с async-кодом.
- `frameworks.md`: FastAPI, Django, Flask, SQLAlchemy и Alembic, pydantic-settings, логирование, Typer. Читай при работе с веб-слоем, БД, настройками, CLI.

## Приоритеты

1. Правила проекта: `.opencode/AGENTS.md`, вложенные `AGENTS.md`, раздел «Проектные правила» агента, конфиги (`pyproject.toml`, `ruff.toml`, `mypy.ini`, `setup.cfg`, CI).
2. Стиль окружающего кода.
3. Значения этого скилла: они применяются только там, где проект сам ничего не задаёт. Конфиги проекта не меняй, пока тебя об этом не просили.

Стиль кода следует PEP 8 (детали ниже), если проект не задал своё. Перед применением определи по репозиторию: версию Python, форматтер и линтер, проверку типов, длину строки. Не определено и от этого зависит результат: спроси, не угадывай.

## Структура кода

- Layout `src/<пакет>/` с тестами в `tests/`, если проект уже не использует другой.
- Внешние зависимости (БД, HTTP, файлы) передаются через параметры конструктора или функции, а не через глобальные синглтоны.
- Модуль решает одну задачу. Не создавай пакеты `utils`/`helpers`/`common` как свалку: назови модуль по смыслу.

## Типизация

- Аннотируй параметры, возвращаемые значения и публичные атрибуты. Для новых проектов проверка типов в строгом режиме; в существующем коде не ужесточай настройки без просьбы.
- Современный синтаксис в рамках версии проекта: `list[str]`, `X | None` (Python 3.10+; для более старых `from __future__ import annotations` или `Optional`).
- Структурированные данные: `dataclass(frozen=True, slots=True)` или pydantic-модель на границах системы (ввод и вывод), `TypedDict` для словарей известной формы, `Protocol` для интерфейсов, `Enum`/`Literal` вместо магических строк.
- `Any` только на границе с нетипизированным кодом, с комментарием, почему. `# type: ignore` только с кодом ошибки и причиной.
- Для результата, который может быть ошибкой по бизнес-причине, допустим явный тип результата (`Result`, объединение типов), если проект так делает. Иначе исключения.

## Ошибки и логирование

- Свои исключения наследуются от одного базового исключения пакета, имя заканчивается на `Error`.
- Голый `except:` и `except Exception: pass` запрещены. Пробрасывая другое исключение, пиши `raise NewError(...) from exc`.
- На границах (HTTP, очередь, CLI) ошибки переводятся в ответ или код выхода, внутри домена остаются исключениями.
- Логи через `logging` (или `structlog`, если проект использует), не `print`. Сообщение с контекстом: что делали, над каким идентификатором.
- Внешние вызовы (сеть, БД, файловая система) имеют таймаут. Повтор только для идемпотентных операций, с ограничением числа попыток.

## Стиль

- Форматирование и импорты ведёт инструмент проекта (чаще всего `ruff format` и `ruff check --fix`). Вручную не спорь с форматтером.
- Отступ 4 пробела, без табуляции. Длина строки по PEP 8: 79 символов, для комментариев и docstring 72. Команда может увеличить лимит строки кода до 99 (комментарии и docstring остаются 72); значение проекта важнее.
- Импорты в начале файла после docstring модуля, по одному на строку, тремя группами с пустой строкой между ними: стандартная библиотека, сторонние пакеты, свой код. Абсолютные импорты предпочтительнее относительных.
- Имена: `snake_case` для функций, методов, переменных и модулей (модули короткие, строчные); `PascalCase` для классов и исключений; `UPPER_CASE` для констант; `_имя` для внутреннего. Не называй переменные `l`, `O`, `I`. Имя говорит о смысле, не о типе.
- Сравнение с `None` только через `is`/`is not`; булево значение не сравнивай с `True`/`False` (`if flag:`); пустую последовательность проверяй как `if not items:`.
- Функцию, которой нужно имя, объявляй через `def`, а не присваиванием `lambda`.
- Все ветки функции либо возвращают значение, либо ни одна: если где-то `return значение`, в остальных местах пиши явный `return None`.
- Функция короче экрана. Больше четырёх позиционных параметров: именованные параметры или объект.
- Не используй изменяемые значения по умолчанию (`def f(x=[])`). Используй `None` и создавай внутри.
- Пути через `pathlib`, файлы через `with`, строки через f-строки, ресурсы через контекстные менеджеры.
- Docstring у публичных модулей, функций, классов и методов (PEP 257), в формате проекта (Google или NumPy; определи по коду).
- Не используй `assert` для проверки пользовательского ввода (его убирает `-O`).

## Антипаттерны

- Глобальное изменяемое состояние, синглтоны, импорты с побочными эффектами.
- Циклические импорты (лечатся переносом общего кода, не отложенным импортом внутри функции).
- `from module import *`, копирование кода вместо переиспользования, длинные цепочки `if/elif` вместо словаря или `match`.
- Проверка типа через `type(x) == T` вместо `isinstance`.
- `eval`/`exec`, `pickle` для недоверенных данных, `shell=True` с пользовательским вводом.
