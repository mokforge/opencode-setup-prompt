# Python: Тестирование с pytest

## Приоритеты

Расположение, именование, фикстуры, маркеры, команда запуска и порог покрытия берутся из проекта (раздел «Проектные правила» tester, `conftest.py`, `pyproject.toml`). Значения ниже работают там, где проект ничего не задаёт. Если проект использует `unittest` или другой фреймворк, следуй ему.

## Структура и именование

- Структура AAA: подготовка (Arrange), действие (Act), проверка (Assert), разделены пустыми строками.
- Имя: `test_<что>_<условие>_<ожидание>`, например `test_withdraw_insufficient_funds_raises`.
- Файлы `test_<модуль>.py` в `tests/`, зеркально структуре пакета. Общие фикстуры в `conftest.py` ближайшего каталога.

## Фикстуры и параметризация

```python
import pytest

@pytest.fixture
def account() -> Account:
    return Account(balance=100)

@pytest.mark.parametrize(
    ("amount", "expected"),
    [(0, 100), (30, 70), (100, 0)],
    ids=["zero", "partial", "all"],
)
def test_withdraw_valid_amount_reduces_balance(account, amount, expected):
    account.withdraw(amount)
    assert account.balance == expected

def test_withdraw_insufficient_funds_raises(account):
    with pytest.raises(InsufficientFundsError, match="insufficient"):
        account.withdraw(1000)
```

- Область фикстуры минимальная (по умолчанию `function`). `session`/`module` только для дорогих неизменяемых ресурсов.
- Подготовка с очисткой: `yield` внутри фикстуры. Временные файлы: `tmp_path`. Переменные окружения и атрибуты: `monkeypatch`.
- Фабрики фикстур вместо множества почти одинаковых фикстур.

## Моки

- Мокай границы системы (сеть, время, файловая система, внешние сервисы), а не собственный код.
- Патчь там, где имя используется, а не где определено: `mocker.patch("пакет.модуль.имя")`.
- Для мока с типом интерфейса используй `autospec=True` или `create_autospec`, чтобы мок не принимал несуществующие вызовы.
- Проверяй результат и наблюдаемые эффекты; `assert_called_with` только там, где сам вызов является поведением (отправка письма, запись в очередь).
- Время: `freezegun` или `time-machine`, не `sleep`.
- Проверка повторов (retry) в коде: замокай вызов, который падает N раз, и проверь число попыток и итог.

## Асинхронные тесты

- Используй плагин проекта (`pytest-asyncio` или `anyio`); режим (`asyncio_mode = "auto"` или маркер `@pytest.mark.asyncio`) возьми из конфигурации проекта.
- Асинхронные фикстуры объявляются тем же способом, что и тесты.
- Ограничивай время ожидания (`asyncio.timeout`), чтобы зависший тест не вешал набор.
- Для HTTP-клиентов и серверов используй тестовые клиенты фреймворка (`httpx.AsyncClient` с ASGI-транспортом), а не реальную сеть.

## Интеграционные тесты и БД

- Отдельные маркеры (`integration`, `slow`) и возможность запустить unit-тесты без внешних сервисов.
- БД: транзакция на тест с откатом или чистая схема на запуск. Не используй общие данные между тестами.
- Миграции проверяй: применение с нуля и откат, если инструмент это поддерживает.
- Внешние HTTP-сервисы в тестах заменяй записанными ответами или заглушкой (`respx`, `responses`), не реальными вызовами.

## Покрытие

- Покрытие показывает, где нет проверок, но не качество тестов. Порог берётся из проекта; новый код не должен его снижать.
- Измеряй ветки (`--cov-branch`), если проект так делает.
- Строки, исключённые из покрытия, помечай с причиной.

## Отладка падающего теста

1. Запусти один тест: `pytest путь::имя -x -vv` (команду проекта подставь из «Проектные правила»).
2. Прочитай реальное и ожидаемое значение, а не догадывайся.
3. Определи причину: дефект кода, устаревшее ожидание или нестабильность окружения (время, порядок, общее состояние, сеть).
